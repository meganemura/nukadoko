# 意図のファイル

変更は、判定される作業より前に、何を違うようにするつもりかを、リポジトリの最上位の `INTENT.md` で宣言します。
レビューする人は、書かれた意図を承認します。
そのあと機械が、実際の振る舞いの変化を意図と比べます。
nukadoko はそうした機械の 1 つです。
`nuka run --base <ref>` は、シナリオの実行イベントに対してこのファイルを読みます([docs/spec.ja.md](spec.ja.md) の「変更の意図」を参照)。
このページは書式だけを書きます。
アプリケーション自身がすべての契約の決定を比べるツールのような、ほかのツールが、nukadoko なしで同じファイルを読めるようにするためです。

## ファイルの場所と、どのファイルが数えられるか

- ファイルは、リポジトリの最上位の `INTENT.md` です。
- ファイルは、それを書いた変更のものです。
  基点が同じテキストで持つファイルは前の変更の意図で、読み手はそれを無視します。
- 変更の最初のコミットで書きます。
  そのあとファイルを変えるコミットは意図の変化で、レビューする人はそれをそのように読みます。
  nukadoko は、意図を宣言したコミット、それが最初のコミットだったか、そのあと意図を変えた各コミットを名指します。

## 表

ファイルは Markdown です。
読み手が読む表は 1 つです。
見出しの行がちょうど次のとおりである最初の表を、表の行でない最初の行の前まで読みます。
その前後の文は人のためのものです。

```markdown
| Target | Observation | Before | After |
| --- | --- | --- | --- |
| x_result.reason=plan:team x_result.seats>=10 | x_decision x_result.features | ["projects","sso"] | ["projects","sso","audit_log"] |
```

セルは 2 つの `|` のあいだのテキストを、前後の空白を除いたものです。
セルの中の `|` は `\|` と書きます。
見出しがあって行の無い表は、何も変わらないことを宣言します。

各行は 1 つの主張です。
対象が名指す行について、観測するものが前から後へ動く、という主張です。

## 項

対象と観測は、空白で区切った項です。

- `field<op>value` は、行のフィールドがその値のとき成り立ちます。
  `op` は `=`、`!=`、`<`、`<=`、`>`、`>=` のどれかです。
  大小は、2 つの数か 2 つの文字列のあいだでだけ比べます。
  そのフィールドを持たない行では、どの項も成り立ちません。
- フィールドは行の中へのドット区切りの道筋です。
  `x_result.seats` は、行の `x_result` オブジェクトの `seats` です。
- 値は、JSON として読めるときは JSON で、そうでなければ書いたとおりのテキストです。
  `plan:team` と `"plan:team"` は同じ値で、`10` は数、`"10"` は文字列です。
  空白を含む値は `"two words"` のように JSON で書きます。
  項は、JSON の文字列の外かつ括弧の外にある空白で終わるので、`["a", "b"]` は 1 つの値です。

## 列

| 列 | 持つもの |
| --- | --- |
| Target | 行が扱う受け入れ基準か行。`@tag` の項と `field<op>value` の項で、すべてが成り立つ必要があります。空ならすべてです。 |
| Observation | [docs/execution-events.ja.md](execution-events.ja.md) の行の種類、観測する行を絞る `field<op>value` の項、そして多くとも 1 つの値の無いフィールド(その値を観測するフィールド)です。 |
| Before | 基点で観測するものです。 |
| After | 変更のあとで観測するものです。 |

- 対象の `field<op>value` の項は、観測する行の上で読みます。
  そのため、決定の対象についての条件は、決定の行そのものに書きます。
  行が対象を `x_subject` に持つなら `x_subject.plan=team` のようにです。
- `@tag` の項はシナリオの tag を名指します。
  シナリオを持たないツールはこれを評価できず、その行を自分の比較が届かないものとして報告します。
- 種類は `request`、`db`、`http`、`job`、`flag`、`error` か、`x_` で始まる書き手自身の種類です。
  書式の種類のフィールドは、粗い実行経路が保つものです。
  `request` は `method`、`route`、`status`、`db` は `table`、`op`、`http` は `method`、`origin`、`path`、`status`、`job` は `name`、`phase`、`flag` は `name`、`side`、`error` は `class`、`handled` です。
  データベースの読み取りはどの実行経路にも入らないので、`db op=read` は何にも当てはまりません。
  書き手自身の種類のフィールドは `x_` で始まります。
- 観測するフィールドが無いとき、前と後は整数です。
  1 つの step が作る、観測する行の数です。
  新しい呼び出しなら `0` と `1` です。
- 観測するフィールドがあるとき、前と後はそのフィールドの値です。
  その行は、前を持っていた行が、同じ数だけ後を持つようになると言います。
- 前と後がどちらも空のとき、その行は、観測するものが何であれ変わらないと言います。
  リファクタは、どの決定も変わらないと言うために `| | x_decision x_result | | |` と書きます。
  前と後は、どちらも埋めるか、どちらも空にします。

## 行の結果

ツールは各行を次のどれかとして報告します:

| 結果 | 意味 |
| --- | --- |
| `as_intended` | 行が扱うものはどれも、行が言うとおりにしました。 |
| `not_happening` | 行が扱うもののどれかが、行が言うとおりにしませんでした。動かなかった数や値、または変わらないと言う行で動いたものです。 |
| `not_reached` | 比較は、行が扱うものを見つけませんでした。ほかの比較が届くかもしれません。 |

ツールが見つける各違いは、どれかの行が宣言しているか、意図していないものです。
ツールは、意図していない違いと、`not_happening` の行で失敗します。
`not_reached` の行は、それだけでは何も失敗させません。
どの比較がそれを扱うべきかを言います。

## 数行で書ける読み手

ほかの言語の読み手は、表の各行を `\` が前に無い `|` で分け、各セルの前後の空白を除き、セルを JSON の文字列と括弧の外にある空白で項に分けます。
次の JavaScript が行を読みます:

```js
const lines = text.split(/\r?\n/);
const at = lines.findIndex((line) => /^\|\s*Target\s*\|\s*Observation\s*\|\s*Before\s*\|\s*After\s*\|\s*$/.test(line));
const rows = [];
for (const line of lines.slice(at + 2)) {
  if (!line.trim().startsWith("|")) break;
  const cells = line.trim().slice(1, -1).split(/(?<!\\)\|/).map((cell) => cell.replaceAll("\\|", "|").trim());
  rows.push({ target: cells[0], observation: cells[1], before: cells[2], after: cells[3] });
}
```
