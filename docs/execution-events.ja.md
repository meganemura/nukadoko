# 実行イベント、版 1

実行イベントは、プログラムが 1 つの操作を終えたときに書く 1 行です。
操作とは、受けたリクエスト、データベースの文、トランザクション、ジョブ、外へ出す HTTP 呼び出し、評価した feature flag、エラーです。
1 つのリクエストの行と、そのリクエストが積んだジョブの行は、1 つの trace id を共有します。
そのため読み手は、そのリクエストの中でプログラムが何をしたかを集められます。
形は、手元のマシンでも、テストの run でも、staging でも、本番でも同じです。

この形式は、読み手を仮定しません。
テストのハーネス、ログのパイプライン、データベースのテーブル、`grep` と `jq` を使う人が、同じ行を読みます。
行の中のどれも、それを読むツールを名指しません。
nukadoko がこの行をどう読むかは、[docs/spec.ja.md](spec.ja.md) の「実行イベント」にあります。

「しなければならない」(must)、「してはならない」(must not)、「するべきである」(should)、「してもよい」(may)は、RFC 2119 の意味で使います。

## 行を書く先

- ファイルは UTF-8 のテキストで、1 行に 1 つの JSON オブジェクトを持ちます。
  各行は 1 つの改行(0x0A)で終わります。
  ファイルにバイト順マークと空行はありません。
- ファイルは、デプロイする側が名指します。
  ふつうは環境変数で名指し、ここでの例は `EXECUTION_EVENTS` を使います。
  パスが無いとき、書き手は何も書かず、プログラムはふだんどおりに動きます。
- 書き手はファイルを追記(`O_APPEND`)で開き、各行を改行も含めて 1 回の write 呼び出しで書きます。
  いくつものスレッドといくつものプロセス(Web サーバとジョブを実行するプロセス、2 つのサーバプロセス)が、こうして 1 つのファイルに追記してもかまいません。
  書き手は、行の一部だけを書いてはならず、操作ごとの終わりに書かずに行を操作をまたいで持っていてはならず、大きな書き込みを分ける stream を通して書いてはなりません。
- 1 行は、改行の前で 4095 バイト以下であるべきです。
  その大きさまでの 1 回の write 呼び出しによる追記は、いくつものプロセスからでも、よく使われるプラットフォームで行のまま保たれます。
  それより長い行は、ほかのプロセスの行と継ぎ合わされることがあります。
  書き手は、それより長い行を書く代わりに、省略できるフィールドを `calls` から順に省きます。
  「種類」にある上限で、ふつうの行はその大きさをはるかに下回ります。
- 書き手は、呼び出しが行をすべて書いたことを確かめるべきです。
  書き込みが短いと壊れた行が残り、読み手はそれを無いものではなく、読めない行として扱います(「trace がそろっていると知る」を参照)。
- ローカルのファイルに追記します。
  ネットワークのファイルシステムは、2 つのホストからの追記を行のまま保たないことがあります。
- 書き手は、読み手が読んでいるあいだに、ファイルを書き直したり、切り詰めたり、ローテートしたりしてはなりません。
  本番のローテートは、読む合間にファイルの名前を変えて新しいファイルを始めます。
  ファイルが短くなったこと、またはそのパスに新しいファイルがあることを見た読み手は、読んだものが欠けているかもしれないとわかります。
- 書き込みの失敗で、操作を失敗させてはなりません。
  書き手はそのことを標準エラーに一度書くべきです。
  「trace がそろっていると知る」の規則が、欠けた行を読み手に見えるようにします。
- 同じ記録をほかの入れ物も持てます。
  1 行につきテーブルの 1 行、1 行につき stream の 1 メッセージです。
  どこに置いても、1 つの JSON オブジェクトが 1 つのイベントです。

## 内側が先

操作の行は、その操作が終わったときに、その中のすべての操作の行のあとに書きます。

- リクエストの行は、そのリクエスト自身の仕事がそのプロセスで書いたどの行よりもあとに来ます。
  本文をストリームするレスポンスでは、行はヘッダを送ったときではなく、本文が終わったとき、またはクライアントが去ったときに書きます。
- トランザクションの行は、コミットしたとき、またはロールバックしたときに書きます。
- ジョブの `perform` の行は、そのジョブのその回の実行のどの行よりもあとに来ます。
- 操作が始めて待たない仕事(スレッド、タイマー、遅らせたコールバック)はジョブです。
  始めるときに `enqueue` の行を、終わるときに `perform` の行を書きます。
  そうしないと、その行はリクエストの行のあとに来ることがあり、読み手はリクエストの仕事がまだ続いていたとわかりません。

この規則があるので、読み手はリクエストの行とジョブの `perform` の行を「中のものはすべて書かれた」として扱えます。

## 共通のフィールド

どの種類も、次のフィールドを持てます。

| フィールド | 型 | 必須 | 意味 |
| --- | --- | --- | --- |
| `trace` | 文字列 | はい | 行が属する trace(下記)。 |
| `kind` | 文字列 | はい | 「種類」にある種類の 1 つ、または `x_` で始まる名前。 |
| `id` | 文字列 | 下記 | この操作の id。1 から 64 文字で、その trace の中で一意。ランダムな小文字の 16 進数 16 文字を勧めます。 |
| `parent` | 文字列 | いいえ | この操作がその中で起きた操作の `id`。同じ trace の中のもの。 |
| `actor` | 文字列 | いいえ | 誰が行ったかを示す、中身の見えない id(ユーザ id、セッション id、そのどちらかのハッシュ)。名前やメールアドレスは決して書きません。 |
| `at` | 文字列 | いいえ | 操作を行ったコードの `path:line`。パスはリポジトリのルートからの相対パス。 |
| `dur_ms` | 数値 | いいえ | 操作にかかった時間。ミリ秒で 0 以上。 |
| `time` | 文字列 | いいえ | 行を書いた時刻。RFC 3339 で UTC、`Z` 付き。 |
| `v` | 整数 | いいえ | 形式の版。無ければ 1。 |

### `trace`

`trace` は W3C Trace Context の `traceparent` の値(`00-<16 進数 32 文字の trace id>-<16 進数 16 文字の親の id>-<16 進数 2 文字のフラグ>`)、または 16 進数 32 文字の trace id だけです。

- リクエストの行は、リクエストが届いたときの `traceparent` ヘッダを、そのまま持ちます。
  呼び出し側はそのヘッダに自分の span id を入れたので、自分が行った呼び出しごとに行を見つけられます。
  正しい `traceparent` でないヘッダは、無いものとして数えます。
- 正しいヘッダが届かなかったとき、プログラムは新しいランダムな trace id と新しいランダムな親の id で 1 つ作り、それが届いたものとして使います。
- リクエストの中で書くすべての行は、リクエストの行と同じ `trace` の値を持ちます。
- ジョブは、それを積んだ操作の `trace` を、ジョブ自身のペイロードに入れて運びます。
  その `enqueue` の行、`perform` の行、実行の中のすべての行がその値を持ちます。
  trace を持つ操作が積んだのでないジョブ(スケジュール、コンソール)は、新しい trace を作ります。
- 外へ出す HTTP 呼び出しは、同じ trace id と、`http` の行の `id` を親の id とする `traceparent` を送るべきです。
  そうすれば、呼ばれたサービスが同じ trace の行を書けます。
- プログラムを呼ぶコマンドラインツールは、空でない環境変数 `TRACEPARENT` の値を、リクエストの `traceparent` ヘッダとして送るべきです。
  これは trace context を環境変数で運ぶ OpenTelemetry の慣例です。
  そうすれば、そのリクエストについてのプログラムの行は、ツールを走らせたものの trace に属します。
- 書き手は小文字で書くべきです。
  読み手は trace id を、大文字と小文字を区別せずに比べます。
  すべて 0 の trace id、すべて 0 の親の id、版 `ff` は正しくありません。

### `id` と `parent`

`id` は、ほかの行が `parent` として名指すすべての行になければなりません。
`request`、`tx`、ジョブの `perform` の行です。
すべての行にあるべきです。

`parent` は、いちばん近い外側の操作を名指します。
トランザクションの中の文はそのトランザクションを、セーブポイントはその外側のトランザクションを名指します。
リクエストの中のトランザクション、flag、ジョブの `enqueue` の行はそのリクエストを、ジョブの実行の中の行はその `perform` の行の `id` を名指します。
リクエストの行とジョブの `perform` の行は、trace の中に `parent` を持ちません。

## 値の規則

- 1 行は 1 つの JSON オブジェクト(RFC 8259)です。
  1 つのオブジェクトに同じキーは二度現れません。
- 整数は -(2^53 - 1) から 2^53 - 1 のあいだです。
  64 ビットの id のような、それより大きい整数は文字列で書きます。
- 文字列は正しい UTF-8 で、対になっていないサロゲートを持ちません。
- `null` は、「種類」が許す場所にだけ書きます。
  省略できるフィールドは、言うことが無いときは省きます。
- 書き手自身のフィールドは `x_` で始まります。
  読み手はそれを残し、それで何も決めません。
  ここで定めておらず、`x_` で始まりもしないフィールドは誤りで、読み手はそれを報告してもかまいません。
- 書き手自身の種類も、同じ規則で `x_` で始まります。
  ここで定めておらず、`x_` で始まりもしない種類は、誤りか、あとの版の種類です。
  行を数える読み手は、そのような行をどの種類でもありうるものとして扱わなければなりません。

## 種類

### `request`: プログラムが受けたリクエスト

| フィールド | 型 | 必須 | 意味 |
| --- | --- | --- | --- |
| `method` | 文字列 | はい | HTTP メソッド。大文字。 |
| `route` | 文字列または `null` | はい | 一致したルートのテンプレート(`/rooms/:room_id/scores`)。値の入ったパスは決して書きません。一致したルートが無ければ `null`。 |
| `status` | 整数 | はい | 送ったステータスコード。 |
| `calls` | 文字列の配列 | いいえ | リクエストが通ったアプリケーションの関数。各定義の `path:line` を、初めて呼んだ順に 1 回ずつ、200 個まで。 |

プログラムが持つすべてのルートを、この同じ語(`method` と `route`)で出力すると、読む人はどの step もリクエストしなかったルートを見つけられます。
[docs/spec.ja.md](spec.ja.md) の「一覧」を参照してください。

### `db`: データベースの文 1 つ

| フィールド | 型 | 必須 | 意味 |
| --- | --- | --- | --- |
| `table` | 文字列 | はい | 文が読んだ、または変えたテーブル。書き手にわからないときは `unknown`。 |
| `op` | 文字列 | はい | `read`、`insert`、`update`、`delete`、`other` のどれか。`other` は、データを変えうる文で、ほかの 3 つのどれでもないもの。どちらの分岐を通ったか書き手が知らない upsert、スキーマの変更、プロシージャの呼び出しです。 |
| `rows` | 整数または `null` | いいえ | 文が変えた、または返した行の数。ドライバが言わないときは `null`。 |
| `ids` | 文字列または整数の配列 | いいえ | 文が変えた行の主キー。欠けがなく 100 個以下のときだけ書きます。それより多いとき、または書き手にわからないときは省きます。 |
| `committed` | 真偽値 | いいえ | 決めるトランザクションが残っておらず変更が永続したとき(文がトランザクションの外で動いたとき)は `true`。永続しなかったと書き手が知っているときは `false`。トランザクションの中では省き、そのトランザクションを `parent` で名指します。 |

プログラムが、各テーブルが何を持つかも同じ語(`table`)で出力すると、読み手はプログラムの状態への書き込みと、プログラム自身の記帳や基盤への書き込みを見分けられます。
[docs/spec.ja.md](spec.ja.md) の「テーブルが持つもの」を参照してください。

### `tx`: トランザクションまたはセーブポイントが終わった

| フィールド | 型 | 必須 | 意味 |
| --- | --- | --- | --- |
| `id` | 文字列 | はい | トランザクションの id。その中の文が `parent` として名指します。 |
| `phase` | 文字列 | はい | `commit` または `rollback`。 |

セーブポイントは、`parent` がその外側のトランザクションである `tx` の行です。
終わらないトランザクション(プロセスが死んだ)は行を持たないので、その中の文の状態はわからないままです(「文の変更が永続したか」を参照)。

### `job`: ジョブを積んだ、またはその実行が終わった

| フィールド | 型 | 必須 | 意味 |
| --- | --- | --- | --- |
| `name` | 文字列 | はい | ジョブの型またはクラスの名前。 |
| `queue` | 文字列 | いいえ | 積んだキュー。 |
| `phase` | 文字列 | はい | `enqueue` または `perform`。 |
| `job_id` | 文字列 | はい | ジョブの仕組みがジョブに付けた id。`enqueue` の行と `perform` の行で同じ値。 |
| `calls` | 文字列の配列 | いいえ | `request` と同じで、その実行についてのもの。 |

- `perform` の行は、ジョブの仕組みがその enqueue を終えたときに書きます。
  ジョブが最後まで動いたとき、例外を投げたとき、動かずに捨てられたときです。
  捨てられたジョブの `perform` の行は、中に行を持ちません。
- もう一度試す実行は、自分の `perform` の行より前に、再試行の `enqueue` の行を書きます。
  再試行は実行の中で決まったからです。
  そのため読み手は、失敗した実行とその再試行のあいだで、ジョブが終わったと見ることがありません。
- 遅らせて積むジョブは、積んだときに `enqueue` の行を、動いたときに `perform` の行を書きます。

### `http`: 外へ出す HTTP 呼び出し

| フィールド | 型 | 必須 | 意味 |
| --- | --- | --- | --- |
| `method` | 文字列 | はい | HTTP メソッド。大文字。 |
| `origin` | 文字列 | はい | `scheme://host`。既定でないときはポート付き。ユーザ情報は決して書きません。 |
| `path` | 文字列 | はい | パス。クエリとフラグメントは無し。クライアントがテンプレートを知っているときはテンプレート。 |
| `status` | 整数または `null` | はい | 受け取ったステータスコード。レスポンスが来なかったときは `null`。 |

### `flag`: 評価した feature flag

| フィールド | 型 | 必須 | 意味 |
| --- | --- | --- | --- |
| `name` | 文字列 | はい | flag の名前。 |
| `side` | 文字列 | はい | プログラムが受け取ったもの。`on`、`off`、または variant の名前。 |
| `gate` | 文字列 | いいえ | それを決めたもの。`boolean`、`actor`、`percentage` のどれか。 |

評価ごとに 1 行を書き、`off` の側も書きます。
2 つの側の経路の違いには、両方が要ります。

### `error`: 投げられたエラー

| フィールド | 型 | 必須 | 意味 |
| --- | --- | --- | --- |
| `class` | 文字列 | はい | エラーのクラスまたはコード。 |
| `handled` | 真偽値 | はい | プログラムがそれを捕まえて続けたときは `true`、それで操作が終わったときは `false`。 |

メッセージのフィールドはありません。
メッセージは値を運ぶからです。
`at` は、エラーを投げた場所を名指すべきです。

## 文の変更が永続したか

読み手は `db` の行のコミットの状態を、その trace の行だけから決めます:

1. 行が `committed` を持つときは、それがその状態です。
   ただし、親をたどった先の `tx` がロールバックしていれば、状態はわかりません。
2. そうでなければ、`parent` が trace の `tx` の行を名指すあいだ、それをたどります。
   たどった `tx` がすべてコミットしていれば、変更は永続しました。
   そのどれかがロールバックしていれば、永続しませんでした。
   たどる先が trace のどの行も(まだ)持たない id を名指すとき、または 1 つの id が 2 つの行に現れるときは、状態はわかりません。
3. `committed` も `tx` の親も持たない行の状態は、わかりません。

読み手は、わからない状態を、どちらの答えとしても決して読んではなりません。
文が動いたトランザクションを名指せない書き手は、どちらも省きます。
そのとき、その文の状態は正直にわからないものになります。

書き手が間違えやすい場合が 2 つあります:

- Rails 8.1 は、セーブポイントまでロールバックするとき、`ROLLBACK TO SAVEPOINT x` を送り、すぐ続けて `RELEASE SAVEPOINT x` を送ります。
  `RELEASE` をコミットとして読む書き手は、ロールバックした書き込みを永続したと報告します。
  2 つの文をセーブポイントの名前で組にし、最初の結果だけを `tx` の行に書きます。
- リクエストの前に始まったトランザクションの中の書き込みは、trace の中にトランザクションの行を持ちません。
  よくある例は、テストが行を残さないようにテストのフレームワークが各テストのまわりで開く、テスト自身のトランザクションです。
  テストのトランザクションはテストが終わるときにロールバックするので、そこでの `committed: true` は偽りです。
  そのような文には、trace のどの行も持たない `parent` を付けます。
  そうすれば、読み手はその状態をわからないものとして決めます。
  Rails では、リクエストが始めたどのトランザクションの外にもある文について、`connection.transaction_open?` が 2 つの場合を見分けます。
  テストのトランザクションの中では true で、文がそれだけでコミットするときは false です。

## trace がそろっていると知る

行の数(「行は書かれなかった」「スコアが 1 つ挿入された」)が意味を持つのは、数える行がすべて書かれたと読み手が知っているときだけです。
この形式は、読み手に次の事実を与えます:

1. **送ったリクエストのそれぞれが、自分の行を持つ。**
   呼び出し側は、送った各 `traceparent` に入れた親の id を知っており、各リクエストの行はそのヘッダを持ち帰ります。
   それらの id のそれぞれについて行がファイルにあれば、内側が先の規則により、そのリクエスト自身の仕事は書かれています。
   `trace` が trace id だけの行は、どれかはわからない 1 つのリクエストを表します。
2. **どのジョブも終わっている。**
   trace の中の各 `job_id` について、ファイルは `enqueue` の行と少なくとも同じ数の `perform` の行を持ちます。
   順序は問いません。
   速いジョブは、リクエストが自分の行を書く前に `perform` の行を書くことがあります。
3. **途中で失われたものがない。**
   読み手が読んでいるあいだに、ファイルは置き換えられず、切り詰められず、短くなりませんでした。

3 つがすべて成り立つまで、数は下限でしかありません。
さらに:

- trace の行が 1 つも無いことは、何も起きなかったという証跡には決してなりません。
  書き手の無いプログラムも、パスを間違えたプログラムも、何も書かないからです。
  事実 1 には、少なくとも 1 つのリクエストの行が要ります。
- 読み手が解析できない行、知らない種類や版の行、数えるときに読むフィールドが無いか正しくない行は、どの行でもありえます。
  そうした行は数の上限を 1 つ上げ、消えることはありません。
- 読み手が決めたあとに届いた trace の行は、trace のすべてより少ないもので決めたことを意味します。
  読み手はその行を遅れた行として分けて持ち、その決定が確定でなかったと言うべきです。
- いくつものプロセスの行は、時刻の順ではなく、書いた順に並びます。
  読み手は、あるプロセスの行がファイルの前のほうにあるからといって、ほかのプロセスの行より前に起きたと仮定してはなりません。

## 行が持ってはならないもの

- 行の値、値の入った文のテキスト、リクエストやレスポンスの本文、ヘッダ、cookie、トークン、エラーメッセージは持ちません。
- 主キーだけを、1 行に 100 個まで持ちます。
- id の入ったパスではなく、ルートのテンプレートを持ちます。
  外へ出すパスはクエリを持ちません。
- `actor` は中身の見えないものです。

trace id と span id は secret ではありません。
行を redact するパイプラインは、16 進数 32 文字と 16 文字の id を丸ごと残すべきです。
trace の行どうしを結び付けるのは、それらの id だからです。

## 版

これは版 1 です。
版 1 の書き手は、`v` を省くか、`1` を書きます。
種類、フィールド、上の規則を変えると新しい版になり、その行は `v` を持ちます。
行の版を知らない読み手は、その行を読めない行として扱います。
それはどの行でもありうるからです。

## 例

あるリクエストがスコアを登録します。

別のプロセスがそのジョブを動かし、トランザクションの外でランキングを更新します。

呼び出し側は `traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01` を送りました。
